# Guitar FX Parameter Predictor — план завершения проекта

> **Цель:** превратить исследовательский ML-проект в воспроизводимое, тестируемое **ML-решение для определения параметров гитарных эффектов по обработанному аудио** с CLI и опциональным API, которое можно показать на собеседовании на ML Engineer / Data Scientist Intern.
>
> **Приоритет:** качественно закончить существующее решение, **не переписывая всё с нуля**. На обязательное ML-ядро ориентир — **15–25 часов**; вместе с FastAPI, Docker и CI — примерно **25–40 часов**.
>
> Этот файл — рабочий план. Отмечай выполненные задачи чекбоксами. Если в актуальном репозитории названия файлов или результаты отличаются, адаптируй шаги под реальное состояние проекта.

## 0. Что уже есть (отправная точка)

- Задача: **multi-output regression** для четырёх параметров эффекта по `wet`-аудио:
  - `room_size_norm`;
  - `wet_level_norm`;
  - `rate_hz_norm`;
  - `depth_norm`.
- Данные: **EGFXSET** (чистые записи) + синтетическая генерация аудио с **Reverb** и **Chorus** через `pedalboard`.
- Ранее получено около **3450 обработанных примеров от 690 исходных записей**.
- Ранее использовалось разбиение по `source_id`: **2415 train / 515 validation / 520 test**. Оно не допускает попадания вариантов одного WAV в разные части, но `source_id` включает pickup (`Bridge_1-0`, `Neck_1-0` и т. п.), поэтому одинаковые позиции `string-fret` пересекаются между split. Исторические метрики нельзя считать финальными до нового разбиения.
- Baseline: XGBoost на аудиопризнаках (`RMS`, `ZCR`, спектральные характеристики, `MFCC`, delta, chroma, spectral contrast). Финальная историческая версия на расширенных признаках: **mean validation R² ≈ 0.657**, **mean test R² ≈ 0.644**, **mean test MAE ≈ 0.133**.
- CNN: PyTorch, mel-spectrogram на входе, 3 convolution-блока, adaptive pooling и early stopping. Исторический эксперимент завершён на 36 эпохах: **mean validation R² ≈ 0.808**, **mean test R² ≈ 0.802**, **mean test MAE ≈ 0.094**. Эти значения — ориентир для проверки воспроизводимости, а не финальное качество из-за старого split.
- Разработка преимущественно на Windows, возможен CPU-only запуск.

**Главный принцип:** сначала корректное разбиение, воспроизводимость и честная оценка, затем чистый PyTorch-пайплайн и inference. API, Docker и новые архитектуры — после завершения ML-ядра.

## 1. Определение MVP и критериев успеха

### Что должно работать на финише

1. После клонирования проекта разработчик может установить зависимости и запустить **инференс на одном `.wav`** по понятной инструкции.
2. Модель возвращает **четыре предсказанных нормализованных параметра**, а при необходимости — их значения в исходных единицах.
3. Есть **CLI** для запуска предсказания без Jupyter.
4. Есть **автоматические тесты**, воспроизводимый расчёт метрик и понятное описание ограничений модели.
5. README объясняет задачу, данные, экспериментальную методологию, результаты и способ попробовать модель.
6. Как инженерное расширение есть **FastAPI endpoint**, а при наличии времени — запуск в **Docker (CPU)**.

### Критерии успеха

- **Обязательно:** корректный group split, рабочий end-to-end CLI inference, воспроизводимые метрики, чистый PyTorch training/evaluation pipeline, тесты и README.
- **Желательно:** FastAPI, Docker, отчёт по ошибкам для каждого таргета, замеры CPU latency, внешний тест на другой записи.
- **Необязательно:** веб-интерфейс, MLflow-сервер, Kubernetes, очереди задач, cloud deploy, новая сложная нейросеть.

- [ ] Зафиксировать два идентификатора:
  - `source_id` — конкретная сухая запись вместе с pickup, например `Bridge_1-0`;
  - `group_id` — позиция `string-fret` без pickup, например `1-0`.
- [ ] Основное разбиение выполнить строго по `group_id`, чтобы все пять pickup-вариантов одной позиции `string-fret` находились только в одной части данных.
- [ ] Добавить автоматические проверки: пересечения `group_id` между train/validation/test должны быть пустыми; все варианты каждого исходного WAV также должны оставаться в одной части.
- [ ] Сохранить старый split только как исторический benchmark и явно не называть его leakage-resistant.
- [ ] Убедиться, что признаки, стандартизация и прочие преобразования обучаются только на train; validation и test не участвуют в их подборе.
- [ ] Проверить корректность целевых нормализаций и преобразований обратно:
  - `room_size = room_size_norm`;
  - `wet_level = wet_level_norm * 0.6`;
  - `rate_hz = rate_hz_norm * 4.5 + 0.5`;
  - `depth = depth_norm`.
- [ ] Проверить отсутствие аудиофайлов с нулевой длиной, NaN/Inf, неожидаемой частотой дискретизации или разным числом каналов.
- [ ] Подтвердить единый preprocessing для обучения и инференса: целевая частота **48 kHz**, mono-конвертация при необходимости, фиксированная обработка длительности (**5 секунд**), одинаковые параметры mel/признаков.
- [ ] Для CNN предварительно вычислять или кэшировать mel-спектрограммы, чтобы не запускать `librosa` заново для каждого примера на каждой эпохе.
- [ ] Сохранить статистику датасета и параметров эффектов в `docs/data.md` или README.

### Результат этапа

## 5. Этап IV — FastAPI-сервис (P1, дни 9–10)

> Переходить к этому этапу только после корректного split, воспроизводимого обучения, CLI и базовых тестов. Для завершённого ML-портфолио CLI достаточен; API — инженерное усиление проекта.

### API-контракт

- `GET /health` → признак готовности приложения и загрузки модели;
- `POST /predict` → загрузка `.wav` через `multipart/form-data`, ответ JSON с 4 параметрами;
- документация Swagger → `/docs`.

### Задачи

- [ ] Вынести логику ML в отдельный сервис, **не писать preprocessing внутри router**.
- [ ] Добавить Pydantic response schema.
- [ ] Обрабатывать некорректные файлы через информативные 4xx-ответы; внутренние ошибки не выдавать пользователю с traceback.
- [ ] Ограничить объём загрузки и декодированного аудио, предусмотреть неподдерживаемые типы файлов.
- [ ] Загрузить модель один раз при старте приложения (lifespan или аналогичный механизм).
- [ ] Проверить запросы через Swagger UI и `curl`/Python-клиент.
- [ ] Описать формат ответа, единицы измерения и ограничения в README.

Пример запуска:

```bash

```

Пример запроса:

```bash
curl -X POST "http://localhost:8000/predict" -F "file=@examples/sample.wav"
```
